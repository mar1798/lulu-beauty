### ✅ Найдено сверх плана и **исправлено**: несуществующий товар не отвечал

Было (прод, до правки):

```
GET /catalog/anua-heartleaf-77-soothing-toner   → 200 за 0,47 с
GET /catalog/zzz-test                           → ответа нет, таймаут 90 с
```

Любой слаг, которого нет в каталоге, висел без ответа — ни 404, ни 200, ни
единого заголовка. Существующий товар при этом отдавался мгновенно.

**Причина.** Страница товара стояла на `fallback: true`. Комментарий в коде
объяснял выбор тем, что каркас — редкость: `getStaticPaths` пререндерит весь
каталог. В проде этого не происходит **никогда**: образ собирается без доступа
к API (так задумано, `apps/website/Dockerfile`), `getStaticPaths` уходит в свой
`catch` и отдаёт пустой список. То есть холодная генерация в проде — не
исключение, а единственный путь, которым вообще появляется страница товара. И
на этом пути `fallback: true` зависал.

Диагностика, которая это показала: тот же URL с User-Agent Googlebot отвечал
**404 за 0,3 с**. Для бота Next рендерит блокирующе независимо от `fallback` —
то есть рабочим в проде был ровно блокирующий путь, а ломался тот, по которому
ходят люди.

**Исправление** (`pages/catalog/[slug].tsx`): `fallback: 'blocking'` в обеих
ветках `getStaticPaths`. Холодный адрес рендерится на сервере и приезжает
готовым — товаром или честным 404. Заодно ушёл сам каркас: `Partial`-пропсы,
`router.isFallback` и `ProductDetailsSkeleton` на странице больше не нужны, а
поисковик физически не может получить HTML со скелетоном.

Проверено на продовой сборке локально (образ собран с недоступным API — ровно
как в CI, кеш ISR очищен):

```
холодный товар, UA браузера     → 200 за 0,09 с, в HTML <h1> с названием, каркаса нет
холодный несуществующий, браузер → 404 за 0,02 с
холодный несуществующий, Googlebot → 404 за 0,01 с
```

`npm run check` — чисто.

**Цена правки:** первый посетитель холодного товара ждёт серверный рендер
(сотни миллисекунд) вместо мгновенного каркаса. Дальше страница живёт в кеше
ISR, а протухшую версию `revalidate` отдаёт сразу и обновляет в фоне.

**Что это меняет для SEO:** для Googlebot ничего (он и раньше получал 404) —
но живые посетители больше не упираются в зависшую вкладку, и критерий
задачи 2.4 («ни один URL не отдаёт 404 молча/неправильно») теперь проверяем.

## 3. Конфликты плана с текущей архитектурой

Плану нужен отдельный разбор: он написан под App Router, а проект на Pages Router.
Ни одна из этих правок не меняет архитектуру — меняется способ, а не результат.

1. **`app/robots.ts`, `app/sitemap.ts`, `MetadataRoute`, `generateMetadata`,
   `metadataBase` — всего этого в Pages Router нет.** Эквиваленты:
   `robots.txt` остаётся статикой в `public/` (он уже есть и корректен, нужна
   только строка `Sitemap:`); карта сайта — `pages/sitemap.xml.ts` с
   `getServerSideProps`, пишущим XML в `res`; метаданные — существующий
   `PageMeta`, в него добавляются `canonical` и формулы; роль `metadataBase`
   уже играет `publicConfig('siteUrl')`.
2. **Примеры кода в плане (`p.price`, `p.volume`, `p.image`) не совпадают с
   моделью.** Реально: `priceCents` (целые копейки — правило «деньги целыми
   `*_cents`» из `CLAUDE.md`), `volumeMl` (число, не «250 мл»), `images[]` с
   выбором `isPrimary`. Формулы это переживают, но писать их нужно по факту.
3. **У бренда нет ни сущности, ни слага** — только строка в товаре. Для
   `/brands/[slug]` нужен маппинг слаг → название. Минимально — таблица
   соответствий на фронте; правильно — справочник брендов в API (миграция).
4. **Фаза 4 = миграция БД + админка + импорт.** Девять новых полей — это
   изменения в модели, схемах, форме товара в админке и xlsx-импорте. Миграция
   обязана быть **расширяющей** (`CLAUDE.md`: прод не откатывает миграции).
5. **Задача 2.4 закрыта, но не буквой плана.** Товар без наличия страницу не
   теряет (`in_stock: false`), снятый — теперь отвечает **временной**
   переадресацией в каталог: публичная ручка различает «слага не было» (404) и
   «товар снят» (410 `product_gone`). Постоянной переадресации из плана здесь
   быть не может: снятие обратимо по устройству — импорт xlsx оживляет товар,
   который встретил снова, а админка умеет восстанавливать вручную, и
   запомненный браузером 301 открывал бы вернувшийся товар каталогом.
6. **`ItemList`/`ISR` на категориях**: страницы каталога статические и
   фильтруются на клиенте через SWR. Категорийные маршруты придётся собирать
   своим `getStaticProps` на товарах категории, иначе в HTML не будет списка,
   который и должен индексироваться.
7. **Аналитика (`@next/third-parties/google`, раздел 9)** потребует правки CSP
   в `next.config.js` — иначе скрипт молча не загрузится (`CLAUDE.md`).
