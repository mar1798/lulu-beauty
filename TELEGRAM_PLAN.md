# План: развитие Telegram-бота Lulu Beauty

Продолжение [`PLAN.md`](./PLAN.md) — раскрывает то, что там закрыто одним пунктом 6 («Telegram-бот (`/start` + привязка контакта), подключить OtpService + напоминания»). Фронтенд описан в [`FRONTEND_PLAN.md`](./FRONTEND_PLAN.md); здесь только `apps/api/app/telegram/` и его вызывающие.

## Текущее состояние (по коду, а не по плану)

Весь бот — ~110 строк в `apps/api/app/telegram/`.

**`bot.py` — три хендлера и жизненный цикл:**

- `/start` (`bot.py:21`) — `@dispatcher.message(F.text == "/start")`, **точное** сравнение. Отвечает `ReplyKeyboardMarkup` с единственной кнопкой `request_contact=True`.
- `message.contact` (`bot.py:35`) — нормализует номер через `app/common/phone.py::normalize_phone`, ищет `User` по телефону: нашёл → проставляет `user.telegram_chat_id`; не нашёл → апсертит `PendingTelegramContact(phone, chat_id)`. Позже `AuthService.register` (`auth/service.py:43`) подхватывает pending-запись при создании пользователя и удаляет её.
- catch-all `handle_fallback` (`bot.py:67`) — регистрируется последним, логирует `content_type`/`text` и просит отправить `/start`.
- `start_polling()`/`stop_polling()` зовутся из `lifespan` (`main.py:24`, `main.py:28`). Бот выключается сам (`bot = None` в `_create_bot()`), если `TELEGRAM_BOT_TOKEN` пуст или синтаксически невалиден.

**`service.py` — `NotificationsService`, ровно два исходящих сообщения:**

- `send_otp` — код регистрации/входа, зовётся из `OtpService.send` (`auth/otp_service.py:45`);
- `send_reminder` — «корзина будет очищена», зовётся из `CycleSchedulerService._remind_cycle` (`cycles/scheduler_service.py:58`) за 24 ч до дедлайна (`REMINDER_WINDOW`).

Обе доставки — best-effort: нет бота или нет `chat_id` → сообщение уходит в лог (`_try_send`, `service.py:51`), а `register`/`login`/рассылка не падают. Дедлайн форматируется в `CYCLE_TIMEZONE` (`_format_deadline`, `service.py:13`).

**Ключевая характеристика архитектуры:** бот сегодня — **односторонний канал доставки**. Он умеет привязать чат и отправить два типа уведомлений. Он ничего не читает из домена: нет ни одной команды, показывающей пользователю его данные, нет ни одного уведомления владельцу, и **нет обратного поиска `chat_id → User`** — везде идёт только `User → chat_id`.

## Расхождения и ловушки, найденные при сверке

Каждое — реальная преграда, в которую упрётся реализация, если не учесть заранее.

1. ~~**Deep-link с payload не работает.**~~ — **закрыто на шаге 1–2**: фильтр `/start` заменён на `CommandStart()`, который матчит и `/start`, и `/start <payload>`. Причина ниже осталась для истории.
   `F.text == "/start"` — точное сравнение, а `t.me/<bot>?start=<nonce>` присылает `"/start <nonce>"` и уходит в fallback: человек получает ответ без кнопки «поделиться контактом» и застревает. Уже учтено во фронтенде (`TelegramLinkPrompt.tsx:12` ведёт на чистый `https://t.me/<username>`), но **любая** будущая фича с deep-link (привязка по nonce, Mini App, реферальные ссылки) упиралась бы в это первой.
2. ~~**Повторный шаринг чужого контакта из того же чата уронит хендлер.**~~ — **закрыто на шаге 1–2** и **подтверждено живьём**: воспроизведено на реальном Postgres (`UniqueViolationError` на `pending_telegram_contacts_chat_id_key`), то есть находка была не теоретической. Теперь каждая привязка сначала снимает чат с прежнего владельца (`recipients.release_chat`), обе ветки покрыты тестами.
   `chat_id` объявлен `unique=True` и в `User.telegram_chat_id` (`auth/models.py:30`), и в `PendingTelegramContact.chat_id` (`telegram/models.py:16`). Сценарий: чат X делится телефоном A → запись создана; затем тот же чат X делится телефоном B → `handle_contact` ищет по телефону B, ничего не находит и вставляет второй ряд с тем же `chat_id` → `IntegrityError` из `session.commit()` внутри хендлера, не пойманный ничем.
3. ~~**Отвязаться невозможно.**~~ — **закрыто на шаге 2**: команда `/unlink`. Ручки в API по-прежнему нет — с сайта отвязать нельзя, только из чата.
4. **`uv run uvicorn --reload` несовместим с ботом** (`PLAN.md:216`): `WatchFiles` шлёт `SIGTERM`, но фоновая задача `dispatcher.start_polling` не всегда успевает завершиться — два `getUpdates` на один токен, часть апдейтов не долетает до актуального хендлера. Для локальной разработки бота — без `--reload`.
5. ~~**`NotificationsService` растёт линейно.**~~ — **закрыто на шаге 1**: тексты вынесены в `telegram/messages.py` (чистые функции, без I/O), в сервисе остался только транспорт.
6. **Anti-flood отсутствует.** Каждая команда — запрос в БД от неаутентифицированного отправителя, и с шага 2 таких команд пять. Сознательно не закрыто: middleware с троттлингом — отдельная работа, не входившая в шаги 1–2.

## Порядок реализации

Шаги отсортированы по отношению «польза / стоимость». Шаг 1 не требует никакой новой инфраструктуры — только новые методы `NotificationsService` и вызовы из существующих сервисов.

### ~~1. Уведомления, которых явно не хватает~~ — готово

- **Владельцу — о новой заявке.** `OrdersService.checkout` (`orders/service.py:75`) сейчас молчит: владелец узнаёт о заказе, только зайдя в админку. Владелец — обычный `User` с `role=ADMIN`, засеянный по `OWNER_PHONE` (`app/scripts/seed.py`), значит привязывает себя тем же `/start` и имеет `telegram_chat_id` на общих основаниях.
  - **Отправлять после коммита, а не внутри сервиса.** Коммитит роутер (`orders/router.py:95`); уведомление, отправленное из `checkout()` до коммита, соврёт про заявку, если транзакция откатится. То же соображение относится ко всем пунктам ниже.
- **Покупателю — о смене статуса заявки.** `update_status` (`orders/service.py:349`) гоняет `PENDING → CONFIRMED → READY → COMPLETED / CANCELLED` и никого не оповещает. «Ваша заявка готова к выдаче» — ровно то, ради чего человек привязывает Telegram. Текст под каждый статус свой; на `PENDING` (возврат отменённой владельцем) уведомление не шлём.
- **Владельцу — сводка при закрытии цикла.** `CycleSchedulerService._close_cycle` (`cycles/scheduler_service.py:83`) знает момент дедлайна: «сбор „<label>“ закрыт, N заявок на сумму Y» — готовый триггер для закупки. Считается там же одним запросом по `Order.cycle_id`.
- **Покупателям — открытие нового сбора.** `CyclesService.create` (`cycles/service.py:41`) — «приём заявок открыт до 12.06». Здесь впервые понадобится **массовая** рассылка: список получателей (все `phone_verified` с `telegram_chat_id`), throttle под лимиты Telegram (~30 сообщений/с) и устойчивость к `403 bot was blocked` — в отличие от точечных отправок выше, тут молча глотать ошибку доставки уже недостаточно, заблокировавший бота пользователь должен терять привязку.

### ~~2. Входящие команды — бот как тонкий клиент~~ — готово

Требует того самого обратного поиска `chat_id → User`, которого сейчас нет; его и завести первым, одной функцией в `telegram/service.py`, вместе с ответом «чат не привязан, отправьте /start» для неизвестных чатов.

- `/orders` — мои заявки со статусами (`OrdersService.list_for_user` уже есть).
- `/cart` — что в корзине и сколько осталось до дедлайна.
- `/deadline` — когда закрывается текущий сбор (`CyclesService.get_active_cycle`, помнить про `None`).
- `/help` — список команд.
- `/unlink` — снять привязку (закрывает п. 3 ловушек).

Заодно закрыть п. 2 ловушек: `handle_contact` обязан сначала снимать `chat_id` с прежнего владельца, а уже потом проставлять новому.

### ~~3. Инлайн-кнопки~~ — готово

`aiogram` в зависимостях, но `InlineKeyboardMarkup` не используется нигде. Кандидаты: «Подтвердить» / «Отменить» прямо под уведомлением владельцу о новой заявке (шаг 1), «Оформить заявку» ссылкой на сайт под напоминанием о корзине. Требует `callback_query`-хендлеров и проверки, что нажимающий — действительно владелец.

### 4. Webhook вместо polling

Мотив не в производительности, а в двух вещах сразу: снимает конфликт с `--reload` (п. 4 ловушек) и убирает фоновую задачу из `lifespan`. Нужен публичный HTTPS-эндпоинт и `secret_token` в заголовке — то есть имеет смысл делать под реальный деплой, а не «на будущее». Держать оба режима за настройкой (`TELEGRAM_USE_WEBHOOK`), чтобы локально остался polling.

### 5. Telegram Login Widget

Сейчас вход = пароль + код в Telegram, два шага. Виджет авторизации дал бы вход в один клик для уже привязанных. Работа заметная — проверка HMAC-подписи от Telegram по хешу токена бота, новая ручка `POST /auth/telegram`, ветка в `AuthService` — но убирает целый экран из флоу.

### 6. Mini App

Самое амбициозное. `apps/website` уже отдаёт каталог и корзину, а Telegram WebApp умеет открывать его внутри чата с готовой авторизацией через `initData`. Отдельный UI писать не нужно — нужны проверка `initData` (та же HMAC-схема, что в шаге 5) и выдача JWT. Делать только после шага 5: половина работы общая.

### Шаги 1–2: уведомления + команды

**Модуль `app/telegram/` разложен на слои** — было два файла, стало шесть. Причина в п. 5 «ловушек»: сообщений стало девять вместо двух, и держать их тексты внутри методов доставки уже нельзя.

- `messages.py` (новый) — все тексты, чистые функции без I/O. Сюда же переехал `_format_deadline` и появился `format_price`: бот считает копейки в сомы **той же** формулой, что `packages/widgets/src/atoms/price` на сайте (`1 250 сом`, `19,99 сом`, разряды через U+00A0) — два разных написания одной суммы в одном магазине расходиться не должны. Плюс `plural()` для «позиция/позиции/позиций».

- `notify.py` (новый) — оркестрация уведомлений **после коммита**.
- `bot.py` — остались инстанс бота, диспетчер и жизненный цикл. Добавлен `set_my_commands` на старте (меню «/» в клиенте); сбой публикации меню логируется и **не** мешает боту подняться.

**Шаг 1 — четыре новых уведомления.**

- **Владельцу о новой заявке** (`orders/router.py::checkout`) и **покупателю о смене статуса** (`::update_order_status`).
- **Владельцу — сводка при закрытии цикла**: `sweep_deadlines()` теперь возвращает `list[CycleClosure]` вместо `int` — считает, сколько заявок и на какую сумму, но **не отправляет**; шлёт `app/scheduler.py` после своего коммита. Отменённые заявки в сумму не входят: это список того, что нужно закупить, а отменённое закупать не надо.
- **Покупателям — открытие сбора** (`cycles/router.py::create_cycle`): троттлинг ~25 сообщений/с, `403` от Telegram означает мёртвую привязку → `clear_stale_bindings` снимает её. Без этого каждый следующий сбор платил бы за те же отвергнутые чаты, а уникальный `chat_id` не давал бы человеку перепривязаться после разблокировки.

**Отправка вынесена из запроса, а не только из сервиса.** План требовал слать после коммита; по ходу выяснилось, что этого мало. Первая версия звала уведомление инлайн после `session.commit()` — и тогда checkout покупателя ждал round-trip до Telegram, а таймаут доставки становился таймаутом оформления заявки. Итог: все три request-driven уведомления идут через `BackgroundTasks` и **открывают собственную сессию** (сессия запроса к тому моменту уже закрыта), а `notify_order_status` перечитывает статус из БД, а не берёт его у вызывающего, — ответ уже ушёл, и единственное, что ещё истинно, это строка в таблице.

**`update_status` теперь возвращает `tuple[Order, bool]`** — «сдвинулся ли статус». Админка позволяет нажать статус, на котором заявка уже стоит; без этого флага покупатель получал бы «готова к выдаче» на каждое нажатие и через неделю перестал бы читать бота. Отличить может только сервис — роутер прежнего значения не видит.

**Шаг 2 — пять команд** (`/orders`, `/cart`, `/deadline`, `/unlink`, `/help`) плюс `/start` и catch-all. `/deadline` намеренно открыта и непривязанным чатам: дата закрытия сбора — публичная информация и единственный вопрос, который осмысленно задать **до** привязки. Остальные отвечают «чат не привязан, отправьте /start». `/cart` различает два пустых состояния — «корзина пуста» при открытом сборе и «сбор закрыт» между циклами: советовать «оформите заявку», когда оформлять некуда, — тупик.

### Шаг 3: инлайн-кнопки

**`keyboards.py` (новый) — разметка и её payload.** Не в `messages.py`: тот модуль — слова, а клавиатура единственная часть уведомления, которая **возвращается**. Её `callback_data` переживает само сообщение и должна остаться разбираемой хендлером, каким бы он ни стал через полгода, — поэтому формат лежит рядом с фильтром, который его декодирует, а не рядом с текстами. Формат — `CallbackData`-фабрика aiogram (`order:confirm:<uuid без дефисов>`, 46 байт из 64 разрешённых), так что id заявки едет целиком и серверная таблица «токен → заявка» не нужна.

**`client.py` (новый) — инстанс бота и `NotificationsService`.** Понадобился сразу: хендлеру нужно уведомить покупателя, то есть импортировать `notify`, а `notify` брал сервис из `bot.py`, который импортирует `handlers`. Цикл `handlers → notify → bot → handlers` падает на импорте, до любых тестов. Теперь `client.py` — то, что нужно только для **отправки**, `bot.py` — диспетчер, меню и polling. `otp_service`/`scheduler_service`/`notify` берут сервис из `client`; тесты, патчащие атрибут на самом объекте сервиса, не заметили разницы.

**Владельцу — «Подтвердить» / «Отменить» под уведомлением о новой заявке.** Дальше по цепочке (`READY`, `COMPLETED`) кнопок нет намеренно: это статусы момента, когда товар физически в руках, а не когда листаешь недельной давности уведомление.

- **Проверяется `from_user`, а не чат.** `callback_data` — клиентские данные: кто дотянулся до бота, тот может их повторить, никакой «кнопка была нарисована не тебе» в протоколе нет. Поэтому решает роль нажавшего (`ADMIN`), а не факт доставки сообщения. Для приватного чата, который владелец привязал через `/start`, `from_user.id` и `chat.id` совпадают, а утёкшая в группу кнопка остаётся мёртвой.
- **Отвечают все ветки.** Неотвеченный `callback_query` оставляет в клиенте крутилку на полминуты — «нельзя» и «готово» одинаково стоят ответа. Отдельная ветка на удалённую заявку: уведомление живёт дольше, чем строка в таблице.
- **Текст сообщения переписывается, клавиатура уезжает вместе с ним.** Иначе сообщение продолжает предлагать оба действия, будто ничего не решено, и к нему возвращаются второй раз.
- **Покупателю уходит ровно то же уведомление, что из админки** — переиспользован `notify_order_status`, включая флаг «статус реально сдвинулся»: нажатие кнопки здесь обязано значить то же, что нажатие там.

**Покупателю — «Оформить заявку» под напоминанием о корзине.** Напоминание существует ради действия, а «найдите сайт сами» — это большая часть пути между «прочитал» и «оформил».

- **Кнопки нет, если адрес не публичный.** Telegram валидирует url-кнопки у себя и на `localhost` (и вообще на хосте без точки) отвечает `BUTTON_URL_INVALID` — а это отказ всего `sendMessage`, не только кнопки. Локально сайт живёт на localhost, так что выбор был между напоминанием без кнопки и отсутствием напоминания.

**Про anti-flood (п. 6 «ловушек»).** Не закрыт и стал заметнее: `callback_query` — ещё один путь в БД от неаутентифицированного отправителя, причём в отличие от команд он пишет, а не читает. Роль проверяется до записи, так что чужой нажим ничего не меняет, но запрос к БД он всё равно стоит.

- **Бот стал точкой входа, а не транспортом для кодов.**
  - `handle_start` принимает payload (`CommandStart()` отдаёт его через `CommandObject.args`) и подтверждает ждущую вкладку: привязанный чат — сразу, непривязанный — после «поделиться номером». Голый `/start` вход не подтверждает: иначе чужое сообщение боту закрывало бы чужую сессию.
  - `handle_contact` теперь **заводит аккаунт**, если номера ещё нет: имя берётся из профиля Telegram (`first_name` + `last_name`, иначе «Покупатель»), номер — из контакта, за который ручается Telegram. Форма регистрации на сайте удалена целиком.
  - `PendingTelegramContact` удалён: он парковал чат до регистрации на сайте, а регистрация теперь и есть этот контакт.
  - `NotificationsService.send_otp` и `messages.otp` удалены — кодов не осталось. Запасной путь «в лог, если чат не привязан» сохранён для остальных уведомлений: привязка обязательна при заведении аккаунта, но умирает, когда бота блокируют.
  - Новые тексты: `LOGIN_CONFIRMED` («вернитесь на вкладку — она уже впустила вас») и `ALREADY_LINKED`. Первый существует потому, что без него человек остаётся в Telegram ждать кода, которого больше не бывает.
  - **Имя берётся из профиля Telegram и больше нигде не спрашивается** — решение осознанное, не пропущенный шаг. Спрашивать его отдельным экраном после первого входа (или диалогом в боте) обсуждалось и отклонено: это шаг для каждого нового покупателя ради случая, который правится в `/account` за десять секунд. Цена известна — в заявке у владельца иногда окажется ник вместо имени (`🌸Настя🌸`, `.`), и он уточнит по телефону, по которому и так звонит.
